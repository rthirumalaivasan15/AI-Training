**Who wrote it:** the claims platform team, not us - we run a local stand-in built to their interface (`claims_system/server.py`), have not reviewed their build, and it identifies itself as `claims-system` version `""` in `initialize`, so we cannot pin or even name the build we would be running.
**What it can reach:** it starts as a child process of our agent with our Windows user's rights and cwd `Week-9`, so it can read any file we can (including `.env` with the Groq key, which the host does not pass it in env); through its two tools it returns status, policy facts and full adjuster notes for any claim number asked for, with no per-claim or per-adjuster scope; and its tool descriptions go verbatim into our model's prompt.
**What it logs:** one line per call in `claims_system/access.log` - UTC time, an 8-character token fingerprint, tool name, claim number (8 lines from this week's runs) - but not the arguments' purpose, which adjuster or agent run asked, or what it returned, and no retention rule is stated; its stderr comes into our host unfiltered.
**What a stolen token could do:** `CLAIMS_API_TOKEN` is one static, non-expiring bearer with no scope, so whoever holds it can walk the sequential CLM-YYYY-nnnnn numbers and read the adjuster notes on every open claim, and the log would show only the same fingerprint our agent uses.
**Ship or don't:** don't ship it for Monday as-is - ship once the team gives a versioned build we can pin, a token scoped per adjuster (or at least notes denied by default) with an expiry, and a caller identity in their log; until then it stays behind the stand-in.
